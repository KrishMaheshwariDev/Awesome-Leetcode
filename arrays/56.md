# 56. Merge Intervals

[LeetCode Problem](https://leetcode.com/problems/merge-intervals/description/)

## 🧩 Problem Understanding

The first thing that came to my mind was:

> **Sort the intervals.**

I'm not completely sure why this was my immediate reaction, but I think the examples influenced it. The intervals were presented in an unsorted order, while intervals naturally make more sense when considered from left to right.

For example:

```text
[8,10] [1,3] [2,6] [15,18]
```

If we sort them by their starting point:

```text
[1,3] [2,6] [8,10] [15,18]
```

the overlapping relationships become much easier to reason about.

And that immediately gives us:

```text
Sorting → O(n log n)
```

So sorting became the first step of my approach.

---

# 🔨 First Approach

After sorting, I initially tried to keep track of:

- `start` → the beginning of the current merge
- `prev` → the interval that I thought represented the latest overlapping interval

The idea was to compare the current interval against the interval represented by `start` and update `prev` whenever an overlap occurred.

### Code

```cpp
class Solution {
public:
    vector<vector<int>> merge(vector<vector<int>>& intervals) {

        // O(n log n) sorting
        sort(intervals.begin(), intervals.end(), [](vector<int> a, vector<int> b){
            return a[0] < b[0];
        });

        int start = 0;
        int prev = 0;

        vector<vector<int>> result;

        for(int i = 1; i < intervals.size(); i++){
            if(intervals[start][1] > intervals[i][0]){
                prev = i;
            }
            else if(intervals[start][1] == intervals[i][0]){
                prev = i;
            }
            else if(intervals[start][1] < intervals[i][0]){
                result.push_back({
                    intervals[start][0],
                    intervals[prev][1]
                });

                start = prev = i;
            }
            else{
                result.push_back(intervals[i]);
                start = prev = i;
            }
        }

        result.push_back({
            intervals[start][0],
            max(intervals[start][1], intervals[prev][1])
        });

        return result;
    }
};
```

### Complexity

The sorting dominates the algorithm:

- ⏱️ **Time:** `O(n log n)`
- 💾 **Space:** `O(n)` for the result

### ❌ Verdict: Wrong Answer

The basic idea of sorting was correct, but the implementation didn't handle all the edge cases.

The problem was deeper than simply checking whether the **current interval overlaps the first interval of the current group**.

Consider:

```text
[1,10]
[2,3]
[4,5]
```

After sorting, we have:

```text
[1,10] [2,3] [4,5]
```

Both `[2,3]` and `[4,5]` are already completely contained inside `[1,10]`.

So the interval we are currently building must continue to be:

```text
[1,10]
```

This made me rethink the state I was maintaining.

---

# 💡 The Key Insight

After some time, I realized:

> **Everything depends on the current merged interval.**

Instead of keeping separate indices such as `start` and `prev`, I could simply put the first interval into the result.

Then every new interval has only two possibilities:

```text
                 New Interval
                      │
                      ▼
            Does it overlap current?
                 /           \
               YES            NO
                │              │
                ▼              ▼
             Merge it       Push it
                │              │
                ▼              ▼
        Update current      New current
                │
                └──────┐
                       ▼
                  Next interval
```

This makes the algorithm much simpler.

---

# ⚡ Optimized Approach

First, sort all intervals by their starting position.

For example:

```text
Before:
[8,10] [1,3] [15,18] [2,6]

After:
[1,3] [2,6] [8,10] [15,18]
```

Now we put the first interval into `result`.

```text
result:
[1,3]
```

Then we process every remaining interval.

## Case 1: Intervals overlap

Two intervals overlap when:

```text
current.start <= previous.end
```

For example:

```text
Current:
[1,5]

New:
   [3,8]
```

Since:

```text
3 <= 5
```

they overlap.

So we merge them:

```text
[1,8]
```

The important part is that the ending point becomes the **maximum** of both endpoints.

```text
newEnd = max(currentEnd, newEnd)
```

This matters for cases like:

```text
[1,10]
[2,5]
```

The merged interval remains:

```text
[1,10]
```

not `[1,5]`.

---

## Case 2: Intervals don't overlap

For example:

```text
Current:
[1,3]

New:
     [5,8]
```

Since:

```text
5 > 3
```

there is no overlap.

So `[1,3]` is finalized, and `[5,8]` becomes the new current interval.

```text
result:
[1,3] [5,8]
```

Then we continue.

---

# 🔄 Complete Flow

```text
                 Sort intervals
                       │
                       ▼
              Push first interval
                 into result
                       │
                       ▼
             Take next interval
                       │
                       ▼
          ┌────────────────────────┐
          │ new.start <= current.end? │
          └────────────┬───────────┘
                   YES │        NO
                       │
             ┌─────────┘ └──────────┐
             ▼                      ▼
      Merge intervals          Push new interval
             │                      │
             ▼                      ▼
 current.end = max(...)       New current interval
             │                      │
             └──────────┬───────────┘
                        ▼
                  More intervals?
                    /       \
                  YES        NO
                   │          │
                   ▼          ▼
                Repeat      Return
```

---

# 💻 Implementation

```cpp
class Solution {
public:
    vector<vector<int>> merge(vector<vector<int>>& intervals) {

        // O(n log n) sorting
        sort(intervals.begin(), intervals.end());

        vector<vector<int>> result;
        result.push_back(intervals[0]);

        int current = 0;

        for(int i = 1; i < intervals.size(); i++){

            if(intervals[i][0] <= result[current][1]){
                result[current] = {
                    result[current][0],
                    max(intervals[i][1], result[current][1])
                };
            }
            else{
                result.push_back(intervals[i]);
                current = result.size() - 1;
            }
        }

        return result;
    }
};
```

# 🧠 Why Sorting Is Necessary

The sorting step is what makes the one-pass merge possible.

Without sorting, we could encounter:

```text
[10,12]
[1,20]
[2,5]
```

and the relationships aren't naturally ordered.

After sorting:

```text
[1,20]
[2,5]
[10,12]
```

Now we can safely process from left to right.

The important property is:

> Once the intervals are sorted by starting position, if the next interval doesn't overlap the current merged interval, it cannot overlap any earlier interval either.

That is what allows us to finalize the current interval and move forward.

---

# 📊 Complexity

Sorting takes:

```text
O(n log n)
```

The subsequent traversal takes:

```text
O(n)
```

Therefore:

```text
O(n log n) + O(n)
= O(n log n)
```

So:

- ⏱️ **Time:** `O(n log n)`
- 💾 **Space:** `O(n)` for the output

There isn't a meaningful general improvement to the comparison-based approach here.

The `O(n log n)` cost comes from sorting, and sorting is what gives us the ordering needed for the simple linear merge pass.

There are specialized possibilities if the interval endpoints have additional constraints, but for the general LeetCode problem, `O(n log n)` is the standard optimal approach.

So yes, this is not a case where some magical C++ compiler incantation will turn it into `O(n)`. 🧙‍♂️

# 🎯 The Real Takeaway

The biggest lesson from this problem wasn't the sorting.

The important realization was:

> **If everything you're doing depends on the current state, make that state explicit.**

Instead of juggling:

```text
start
prev
i
```

I realized I only really needed:

```text
current merged interval
```

Then the entire problem becomes:

```text
             Sorted intervals
                    │
                    ▼
          ┌──────────────────┐
          │ Current interval │
          └────────┬─────────┘
                   │
             Next interval
                   │
             ┌─────┴─────┐
             ▼           ▼
          Overlap      No overlap
             │           │
             ▼           ▼
           Merge       Push
             │           │
             └─────┬─────┘
                   ▼
              Continue
```

### 🧠 Pattern to Remember

**Sorting + Greedy Interval Merging**

When dealing with intervals:

1. **Sort them by start time.**
2. Maintain the **current merged interval**.
3. If the next interval overlaps it, extend the end.
4. Otherwise, finalize the current interval and start a new one.

```text
Sort → Compare → Merge / Push → Repeat
```

**Time:** `O(n log n)`
**Space:** `O(n)` for the output
**Final Verdict:** **Solved 🎯**
