# 152. Maximum Product Subarray

[LeetCode Problem](https://leetcode.com/problems/maximum-product-subarray/description/)

## 🧩 Problem Understanding

After solving **53. Maximum Subarray**, this problem initially looked very similar.

The difference is one word:

> **Sum → Product**

We still need to find a **contiguous, non-empty subarray**, but this time we want the subarray whose product is maximum.

For example:

```text
nums = [2, 3, -2, 4]

Subarray:
[2, 3] → 6
[2, 3, -2] → -12
[3, -2, 4] → -24
[2, 3, -2, 4] → -48

Maximum product = 6
```

So the first instinct was to apply the same general strategy from **Maximum Subarray**.

---

# 🔨 Brute Force Approach

The first intuition was essentially the same as Problem 53:

1. Start from every index.
2. Generate every possible subarray.
3. Maintain the product while extending the subarray.
4. Keep track of the maximum product.

Instead of recalculating the product for every subarray, we can maintain a running product.

For example:

```text
[2, 3, -2, 4]

Start at 2:

2
2 × 3       = 6
2 × 3 × -2  = -12
2 × 3 × -2 × 4 = -48
```

### Code

```cpp
class Solution {
public:
    int maxProduct(vector<int>& nums) {
        int product = INT_MIN;

        for(int i = 0; i < nums.size(); i++){
            int current = 1;

            for(int j = i; j < nums.size(); j++){
                current *= nums[j];
                product = max(current, product);
            }
        }

        return product;
    }
};
```

### Complexity

We have two nested loops, so:

- ⏱️ **Time:** `O(n²)`
- 💾 **Space:** `O(1)`

Unfortunately, just like the brute-force solution for Problem 53, this also resulted in:

> ❌ **Time Limit Exceeded**

So once again, the real question became:

> **Can we solve this in a single pass?**

---

# ⚡ First Attempt: Simple Kadane's Algorithm

Since the problem looked extremely similar to Maximum Subarray, the next idea was obvious:

**Use Kadane's Algorithm.**

For the maximum-sum problem, we only needed to track the best subarray ending at the current position.

So I initially tried to do the same thing here.

The idea was:

```text
Current maximum product
        ↓
Either start from nums[i]
        ↓
or multiply nums[i] with previous maximum
```

### Code

```cpp
class Solution {
public:
    int maxProduct(vector<int>& nums) {
        int maxEndshere = 1;
        int maxSoFar = INT_MIN;

        for(int i = 0; i < nums.size(); i++){
            maxEndshere = max(nums[i], nums[i] * maxEndshere);
            maxSoFar = max(maxSoFar, maxEndshere);
        }

        return maxSoFar;
    }
};
```

But this approach **didn't work**.

❌ **Wrong Answer**

And this failure exposed an important difference between the two problems.

---

# 🧠 Why Doesn't Normal Kadane Work?

The problem is **negative numbers**.

For sums, if we have a negative running sum:

```text
-5
```

adding another number to it will never make the result better than starting from that number itself in the relevant Kadane decision.

But multiplication behaves differently.

Consider:

```text
-2 × -3 = 6
```

A negative value that looks bad right now can become the **best possible value later**.

This means:

> **The minimum product is also important.**

That's the key observation.

---

# 🔄 The Important Pattern: Negative × Negative = Positive

Suppose at some position we have:

```text
nums[i] = -4
```

and the previous subarray has:

```text
maximum product = 5
minimum product = -6
```

Then:

```text
-4 × 5  = -20
-4 × -6 = 24
```

The previous **minimum** suddenly produces the new **maximum**.

This is the critical difference from the Maximum Subarray problem.

```text
             Current Number
                  │
                  ▼
             ┌──────────┐
             │ nums[i]  │
             └────┬─────┘
                  │
        ┌─────────┼─────────┐
        ▼         ▼         ▼
     nums[i]   nums[i] ×   nums[i] ×
                max          min
        │         │           │
        └─────────┼───────────┘
                  ▼
          New Maximum
          New Minimum
```

So instead of tracking only:

```text
maxEndshere
```

we need to track **both**:

```text
maxEndshere
minEndshere
```

---

# 🧩 Three Possibilities

At every element `nums[i]`, there are three possibilities for the maximum product ending at the current position:

### 1. Start a new subarray

```text
nums[i]
```

### 2. Extend the previous maximum

```text
nums[i] × oldMax
```

### 3. Extend the previous minimum

```text
nums[i] × oldMin
```

Therefore:

```text
newMax = max(
    nums[i],
    nums[i] × oldMax,
    nums[i] × oldMin
)
```

And similarly:

```text
newMin = min(
    nums[i],
    nums[i] × oldMax,
    nums[i] × oldMin
)
```

This gives us the complete state transition.

---

# ⚠️ A Small Implementation Problem

When I first tried to maintain both maximum and minimum, the logic was correct in my mind, but the implementation became messy.

The problem was **mixed updates**.

Suppose we write:

```cpp
maxEndshere = ...
minEndshere = ...
```

If `minEndshere` is calculated using `maxEndshere` after it has already been updated, then we're no longer using the values from the **previous iteration**.

That changes the calculation.

For example:

```text
oldMax ───────┐
              ├──→ newMax
oldMin ───────┘

oldMax ───────┐
              ├──→ newMin
oldMin ───────┘
```

Both calculations must use the same old state.

So I decided to explicitly preserve the previous values:

```cpp
oldMax
oldMin
```

Then calculate the new values from them.

Only after both calculations are complete do we update:

```cpp
oldMax = maxEndshere;
oldMin = minEndshere;
```

That keeps the state transition clean.

---

# 🚀 Final Optimized Approach

The complete flow is:

```text
                ┌──────────────┐
                │   nums[i]    │
                └──────┬───────┘
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
       nums[i]    nums[i]×oldMax  nums[i]×oldMin
          │            │            │
          └────────────┼────────────┘
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
         Maximum               Minimum
       ending here            ending here
             │                   │
             └─────────┬─────────┘
                       ▼
                  Update answer
```

At every element, we maintain:

- `oldMax` → maximum product ending at the previous position
- `oldMin` → minimum product ending at the previous position
- `maxEndshere` → maximum product ending at the current position
- `minEndshere` → minimum product ending at the current position
- `maxSoFar` → maximum product found anywhere

### Code

```cpp
class Solution {
public:
    int maxProduct(vector<int>& nums) {
        int maxEndshere = 1;
        int minEndshere = 1;

        int maxSoFar = INT_MIN;

        int oldMax = 1;
        int oldMin = 1;

        for(int i = 0; i < nums.size(); i++){
            maxEndshere = max(nums[i], nums[i] * oldMax);
            maxEndshere = max(maxEndshere, nums[i] * oldMin);

            minEndshere = min(nums[i], nums[i] * oldMax);
            minEndshere = min(minEndshere, nums[i] * oldMin);

            maxSoFar = max(maxSoFar, maxEndshere);

            oldMax = maxEndshere;
            oldMin = minEndshere;
        }

        return maxSoFar;
    }
};
```

---

# 🔍 Walking Through the Important Case

Consider:

```text
[-2, 3, -4]
```

Start with:

```text
oldMax = 1
oldMin = 1
```

### Step 1: `-2`

Possible products:

```text
-2
-2 × 1 = -2
-2 × 1 = -2
```

Therefore:

```text
max = -2
min = -2
```

### Step 2: `3`

Now:

```text
3
3 × (-2) = -6
3 × (-2) = -6
```

Therefore:

```text
max = 3
min = -6
```

Notice that the minimum is getting more negative.

That looks bad for the moment.

But then comes:

### Step 3: `-4`

Now:

```text
-4
-4 × 3  = -12
-4 × -6 = 24
```

And suddenly:

```text
24
```

becomes the maximum.

This is exactly why we cannot throw away the minimum product.

---

# 🧠 The Core Insight

The entire problem can be reduced to one observation:

> **With multiplication, the minimum can become the maximum when multiplied by a negative number.**

For sums:

```text
negative + positive
```

doesn't create the same state reversal.

For products:

```text
negative × negative = positive
positive × positive = positive
```

Therefore, both extremes matter.

```text
             Product Problem
                    │
                    ▼
           Negative numbers?
                    │
                   YES
                    │
                    ▼
       ┌─────────────────────────┐
       │ Minimum can become      │
       │ maximum after × negative│
       └────────────┬────────────┘
                    │
                    ▼
        Track BOTH max and min
```

---

# 🆚 Maximum Subarray vs Maximum Product Subarray

This problem is a good example of why blindly applying a familiar algorithm can fail.

| Problem                  | State we need                               |
| ------------------------ | ------------------------------------------- |
| Maximum Subarray         | Maximum sum ending here                     |
| Maximum Product Subarray | Maximum **and** minimum product ending here |

### Maximum Subarray

```text
maxEndingHere
       ↓
extend or restart
```

### Maximum Product Subarray

```text
                ┌──→ maxEndingHere
nums[i] ────────┤
                └──→ minEndingHere
```

The additional state is necessary because multiplication can reverse the ordering of positive and negative values.

---

# 📊 Complexity

We process every element exactly once.

For each element, we perform a constant number of operations.

Therefore:

- ⏱️ **Time:** `O(n)`
- 💾 **Space:** `O(1)`

This is optimal for a problem where we must inspect every element.

---

# 🎯 Final Takeaway

The brute-force solution taught us that generating every possible subarray is too expensive.

The first Kadane attempt taught us that **maximum alone is not enough**.

The key breakthrough was recognizing:

```text
(-) × (-) = (+)
```

So a value that is currently the **minimum** can become the **maximum** later.

That leads to the final state:

```text
┌─────────────────────────────────┐
│ Maximum Product Ending Here     │
├─────────────────────────────────┤
│ Minimum Product Ending Here     │
└─────────────────────────────────┘
```

At every element, consider:

```text
nums[i]
nums[i] × oldMax
nums[i] × oldMin
```

Then preserve the new maximum and minimum for the next iteration.

### 🧠 Pattern to Remember

**Dynamic Programming + State Tracking**

> When an operation can reverse the ordering of values, tracking only the best state may not be enough. Sometimes the worst state is equally important.

**Brute Force:** `O(n²)` ❌ TLE  
**Optimized:** `O(n)` ✅  
**Extra Space:** `O(1)`  
**Final Verdict:** **Solved 🎯**
