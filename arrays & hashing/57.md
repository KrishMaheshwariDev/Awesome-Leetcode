# 57. Insert Interval

[LeetCode Problem](https://leetcode.com/problems/insert-interval/description/)

## 🧩 Problem Understanding

After solving the previous interval problem, my first intuition here was straightforward:

> **Insert the new interval, sort everything, then merge overlapping intervals.**

The intervals are given in sorted order, but my initial solution did not take advantage of that property.

For example:

```text
intervals = [[1,3], [6,9]]
newInterval = [2,5]
```

If I insert `[2,5]` at the end:

```text
[[1,3], [6,9], [2,5]]
```

then sort:

```text
[[1,3], [2,5], [6,9]]
```

and finally merge:

```text
[[1,5], [6,9]]
```

So the problem naturally breaks into two tasks:

```text
        Insert new interval
                │
                ▼
          Sort intervals
                │
                ▼
        Merge overlapping
                │
                ▼
             Result
```

---

# 🔨 First Approach: Insert + Sort + Merge

My first solution was basically:

1. Add `newInterval` to the end.
2. Sort the complete array.
3. Traverse the sorted intervals.
4. Merge overlapping intervals.

### Code

```cpp
class Solution {
public:
    vector<vector<int>> insert(vector<vector<int>>& intervals,
                               vector<int>& newInterval) {
        intervals.push_back(newInterval);
        sort(intervals.begin(), intervals.end());

        vector<vector<int>> result;
        result.push_back(intervals[0]);

        int current = 0;

        for(int i = 1; i < intervals.size(); i++){

            if(intervals[i][0] <= result[current][1]){
                result[current] = {
                    result[current][0],
                    max(intervals[i][1], result[current][1])
                };
            }
            else{
                result.push_back(intervals[i]);
                current = result.size() - 1;
            }
        }

        return result;
    }
};
```

The merging logic is essentially the same pattern as the previous interval problem.

If the next interval starts before or exactly when the current interval ends:

```text
next.start <= current.end
```

then the two intervals overlap.

Otherwise, the next interval is separate.

### Example

```text
Current:
[1, 3]

Next:
[2, 5]
```

Since:

```text
2 <= 3
```

they overlap.

Merge them:

```text
[1, max(3,5)]
→ [1,5]
```

---

# 📊 Complexity

The expensive part is sorting:

```text
sort(intervals.begin(), intervals.end());
```

Sorting `n` intervals takes:

- ⏱️ **Time:** `O(n log n)`

The merge itself is linear:

- ⏱️ **Time:** `O(n)`

Therefore the overall complexity is:

- ⏱️ **Time:** `O(n log n)`
- 💾 **Extra Space:** `O(1)` apart from the result required by the problem.

The solution was:

> ✅ **Accepted**

But something bothered me.

---

# 🧠 The Important Observation

The problem already gives us an extremely useful guarantee:

> **The intervals are already sorted by their starting positions.**

So why am I sorting them again?

The array looks like:

```text
[1,3] → [6,9] → [12,15] → [20,25]
```

and then I append the new interval:

```text
[1,3] → [6,9] → [12,15] → [20,25] → [7,13]
                                             ↑
                                        new interval
```

Only **one interval is out of position**.

There is no reason to perform a full `O(n log n)` sort.

This changes the problem completely.

---

# ⚡ Optimized Approach: Insert Into the Sorted Position

Since `newInterval` is initially placed at the end, I can move it toward the beginning until it reaches its correct position.

The idea is essentially insertion:

```text
Sorted intervals:
[1,3] [6,9] [12,15] [20,25]

New interval:
[7,13]

Append:
[1,3] [6,9] [12,15] [20,25] [7,13]
                                      ↑
                                      │
                               move left
                                      │
                                      ▼
[1,3] [6,9] [7,13] [12,15] [20,25]
```

I compare the starting positions of adjacent intervals.

If:

```text
interval[i-1][0] > interval[i][0]
```

then they are in the wrong order, so I swap them.

Once the previous interval already has a smaller starting position, the new interval has reached its correct position and I can stop.

### Flow

```text
              Append new interval
                      │
                      ▼
              Start from the end
                      │
                      ▼
       Compare current interval
       with the previous interval
                      │
             ┌────────┴────────┐
             │                 │
      Previous starts       Previous starts
        after current        before current
             │                 │
             ▼                 ▼
           Swap              STOP
             │
             ▼
        Move left
             │
             └───────►
```

This requires at most `O(n)` swaps.

---

# 💻 Optimized Implementation

```cpp
class Solution {
public:
    vector<vector<int>> insert(vector<vector<int>>& intervals,
                               vector<int>& newInterval) {
        vector<vector<int>> result;

        if(intervals.size() == 0){
            result.push_back(newInterval);
            return result;
        }

        intervals.push_back(newInterval);

        for(int i = intervals.size() - 1; i > 0; i--){
            if(intervals[i-1][0] > intervals[i][0]){
                swap(intervals[i-1], intervals[i]);
            }
            else{
                break;
            }
        }

        result.push_back(intervals[0]);

        int current = 0;

        for(int i = 1; i < intervals.size(); i++){

            if(intervals[i][0] <= result[current][1]){
                result[current] = {
                    result[current][0],
                    max(intervals[i][1], result[current][1])
                };
            }
            else{
                result.push_back(intervals[i]);
                current = result.size() - 1;
            }
        }

        return result;
    }
};
```

Now the algorithm becomes:

```text
Append
  │
  ▼
Move interval to correct position
  │
  ▼
Array is sorted
  │
  ▼
Merge intervals
  │
  ▼
Result
```

# 🔍 Example Walkthrough

Consider:

```text
intervals = [[1,3], [6,9]]
newInterval = [2,5]
```

### Step 1: Append

```text
[[1,3], [6,9], [2,5]]
```

### Step 2: Move `[2,5]`

Compare:

```text
[6,9] vs [2,5]
```

Since:

```text
6 > 2
```

swap:

```text
[[1,3], [2,5], [6,9]]
```

Now compare:

```text
[1,3] vs [2,5]
```

Since:

```text
1 < 2
```

we stop.

The intervals are sorted again.

### Step 3: Merge

Start with:

```text
[1,3]
```

Next:

```text
[2,5]
```

Since:

```text
2 <= 3
```

they overlap.

Merge:

```text
[1,5]
```

Next:

```text
[6,9]
```

Since:

```text
6 > 5
```

there is no overlap.

Final result:

```text
[[1,5], [6,9]]
```

🎯

---

# 📊 Complexity

There are two linear operations.

### Insertion

The new interval can move through the entire array:

```text
O(n)
```

### Merging

We traverse the intervals again:

```text
O(n)
```

Therefore:

```text
O(n) + O(n)
= O(n)
```

So:

- ⏱️ **Time:** `O(n)`
- 💾 **Extra Space:** `O(1)` apart from the required result.

This is a significant improvement over:

```text
O(n log n)
```

---

# 🧠 Could We Do Better?

While writing this solution, another optimization came to mind.

The intervals are already sorted.

So instead of linearly moving the new interval to its position, we could use **binary search** to find its insertion position.

That would give:

```text
Binary Search
     │
     ▼
Find insertion position
     │
     ▼
Merge intervals
```

The insertion-position search would become:

```text
O(log n)
```

instead of:

```text
O(n)
```

However, there is an important catch.

The merge operation still requires traversing the intervals:

```text
O(n)
```

So the total complexity would be:

```text
O(log n) + O(n)
```

which simplifies to:

```text
O(n)
```

Therefore, asymptotically, **there is no improvement**.

The current solution is already `O(n)`.

---

# ⚠️ But There Is Still a Potential Practical Optimization

The interesting part is that the binary-search idea becomes more useful if we avoid physically inserting or shifting the interval.

Instead, we could determine where `newInterval` belongs and then process the original intervals while treating that position as an additional interval.

That could reduce unnecessary movement and potentially improve constant factors.

But this is where I would stop for now.

Why?

Because:

```text
O(n)
```

is already optimal in the asymptotic sense. We need to inspect the intervals to determine which ones overlap with the new interval.

Introducing more machinery purely to shave constant factors would make the implementation more complicated without changing the Big-O complexity.

That is a classic case of:

> **Optimization is not automatically improvement.**

---

# 🆚 Approach Comparison

| Approach               | Sorting / Placement |  Merge |            Total |
| ---------------------- | ------------------: | -----: | ---------------: |
| Append + Sort          |        `O(n log n)` | `O(n)` | **`O(n log n)`** |
| Append + Linear Insert |              `O(n)` | `O(n)` |       **`O(n)`** |
| Binary Search + Merge  |          `O(log n)` | `O(n)` |       **`O(n)`** |

So the important improvement was not some exotic algorithm.

It was simply noticing:

```text
❌ "Sort everything."

vs.

✅ "Everything is already sorted except one interval."
```

That observation removed the `O(n log n)` operation completely. 🧠

---

# 🎯 Takeaway

This problem reinforced an important lesson about **using the properties of the input**.

My first solution treated the input as an arbitrary collection:

```text
Insert
  ↓
Sort everything
  ↓
Merge
```

But the input wasn't arbitrary.

It was already sorted.

So the optimized reasoning became:

```text
Already sorted
      │
      ▼
Only one new interval is misplaced
      │
      ▼
Move that interval into position
      │
      ▼
Array remains sorted
      │
      ▼
Merge
```

The key question to ask when you see a sorting problem is not always:

> **"How can I sort this faster?"**

Sometimes it is:

> **"What is already sorted, and what actually needs to move?"**

### 🧠 Pattern to Remember

**Exploit Existing Order**

If a collection is already sorted and only a small number of elements are being introduced or modified, don't automatically throw away that ordering with a full sort.

**Initial:** `O(n log n)` / `O(1)` extra space → ✅ Accepted
**Optimized:** `O(n)` / `O(1)` extra space → ✅ Accepted
**Possible refinement:** Binary search gives `O(log n)` insertion-position lookup, but the required merge remains `O(n)`, so total complexity stays **`O(n)`**.
