# 724. Find Pivot Index

[LeetCode Problem](https://leetcode.com/problems/find-pivot-index/description/)

## 🧩 Problem Understanding

The problem asks us to find an index where:

> **The sum of all elements to the left equals the sum of all elements to the right.**

The pivot element itself is **not included** in either sum.

For example:

```text
nums = [1, 7, 3, 6, 5, 6]
```

At index `3`:

```text
Left side:
1 + 7 + 3 = 11

Right side:
5 + 6 = 11
```

Therefore:

```text
Pivot Index = 3
```

The first thing I thought was straightforward:

> "For every index, calculate the left sum and right sum, then compare them."

---

# 🔨 Brute Force Approach

For every index `i`, I calculate:

```text
left_sum  = nums[0] + ... + nums[i-1]

right_sum = nums[i+1] + ... + nums[n-1]
```

Then:

```text
if(left_sum == right_sum)
    return i;
```

If we reach the end without finding a pivot:

```text
return -1;
```

### Code

```cpp
class Solution {
public:
    int pivotIndex(vector<int>& nums) {
        for(int i = 0; i < nums.size(); i++){
            int left_sum = 0;
            int right_sum = 0;

            for(int j = i - 1; j >= 0; j--){
                left_sum += nums[j];
            }

            for(int k = i + 1; k < nums.size(); k++){
                right_sum += nums[k];
            }

            if(left_sum == right_sum){
                return i;
            }
        }

        return -1;
    }
};
```

# 📊 Complexity

The problem with this approach is that we repeatedly calculate sums that we have already calculated before.

For example, when checking index `3`, we calculate:

```text
1 + 7 + 3
```

But those values were already involved when checking previous indices.

In the worst case, we perform a linear traversal for each index.

Therefore:

- ⏱️ **Time:** `O(n²)`
- 💾 **Space:** `O(1)`

### Verdict

✅ **Accepted**

But there is a lot of repeated work.

And that is usually a good signal that we should think about **prefix sums**.

---

# ⚡ Optimized Approach: Prefix Sum

The main observation is:

> **The sum of elements up to an index can be calculated once and reused.**

Instead of repeatedly calculating:

```text
1 + 7 + 3
```

we can precompute the cumulative sums.

For:

```text
[1, 7, 3, 6, 5, 6]
```

the prefix sums are:

```text
Index:       0   1   2   3   4   5
             ↓   ↓   ↓   ↓   ↓   ↓
Nums:        1   7   3   6   5   6

Prefix:      1   8  11  17  22  28
```

Similarly, we can calculate suffix sums from the right:

```text
Suffix:     28  27  20  17  11   6
```

Now we don't need to repeatedly traverse the array.

---

# 🧠 Prefix + Suffix Visualization

```text
nums:
       1    7    3    6    5    6
       │    │    │    │    │    │
       ▼    ▼    ▼    ▼    ▼    ▼

left:
       1    8   11   17   22   28

right:
      28   27   20   17   11    6
```

At index `3`:

```text
left_sum[3]  = 17
right_sum[3] = 17
```

So we have a match.

However, there is an important detail here.

The prefix and suffix arrays in this implementation **include the pivot element itself**.

At index `3`:

```text
left_sum[3]  = 1 + 7 + 3 + 6 = 17
right_sum[3] = 6 + 5 + 6 = 17
```

Notice that the suffix calculation happens to exclude the elements after the pivot in the way the array is constructed, but the naming can be confusing.

A cleaner conceptual interpretation of the implementation is to think of the two arrays as cumulative totals anchored at each index, rather than literal "elements strictly left" and "elements strictly right."

The implementation works because the equality condition is equivalent to:

```text
total_sum_before_or_at_i
=
total_sum_from_i
```

which, after both sides contain the pivot appropriately, reduces to the same pivot condition.

---

# 💻 Implementation

```cpp
class Solution {
public:
    int pivotIndex(vector<int>& nums) {
        vector<int> left_sum;
        vector<int> right_sum(nums.size());

        int sum = 0;

        // Prefix sums
        for(auto i : nums){
            sum += i;
            left_sum.push_back(sum);
        }

        sum = 0;

        // Suffix sums
        for(int i = nums.size() - 1; i >= 0; i--){
            sum += nums[i];
            right_sum[i] = sum;
        }

        // Find pivot
        for(int i = 0; i < nums.size(); i++){
            if(left_sum[i] == right_sum[i]){
                return i;
            }
        }

        return -1;
    }
};
```

---

# 🔄 How the Optimization Removes Repeated Work

The brute-force approach essentially does this:

```text
Index 0 → calculate sums
Index 1 → calculate sums again
Index 2 → calculate sums again
Index 3 → calculate sums again
...
```

So we repeatedly walk over the same elements.

The optimized approach changes that:

```text
             ┌──────────────┐
             │   Array      │
             └──────┬───────┘
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
   Prefix Sum Pass      Suffix Sum Pass
          │                   │
          ▼                   ▼
     Left totals         Right totals
          │                   │
          └─────────┬─────────┘
                    ▼
             Compare at i
                    │
             ┌──────┴──────┐
             │             │
           Equal        Not equal
             │             │
             ▼             ▼
         Return i      Continue
```

Each pass is linear.

Therefore:

```text
O(n) + O(n) + O(n)
```

which simplifies to:

```text
O(n)
```

---

# 📊 Complexity

We make three linear passes:

1. Build `left_sum` → `O(n)`
2. Build `right_sum` → `O(n)`
3. Find the pivot → `O(n)`

Therefore:

- ⏱️ **Time:** `O(n)`
- 💾 **Space:** `O(n)`

The time complexity is a significant improvement:

```text
O(n²) → O(n)
```

But we introduced additional memory to store the prefix and suffix sums.

---

# 🧠 A Further Optimization

There is actually an even better way to think about this problem.

We don't necessarily need **both arrays**.

We can calculate the total sum of the entire array first:

```text
total = sum(nums)
```

Then maintain a running `leftSum`.

For a pivot at index `i`, the right sum is:

```text
rightSum = total - leftSum - nums[i]
```

So the condition becomes:

```text
leftSum == total - leftSum - nums[i]
```

This gives us a one-pass solution after calculating the total.

The flow becomes:

```text
              Calculate Total
                    │
                    ▼
              leftSum = 0
                    │
                    ▼
              For every i
                    │
                    ▼
        rightSum = total
                   - leftSum
                   - nums[i]
                    │
                    ▼
          leftSum == rightSum?
              /           \
            Yes            No
             │              │
             ▼              ▼
          Return i      leftSum += nums[i]
```

This reduces the extra space from `O(n)` to `O(1)`.

So while the prefix/suffix implementation is already a major improvement, the problem actually allows an even cleaner solution.

---

# 🎯 Takeaway

This problem is a good introduction to the **prefix sum pattern**.

The brute-force approach repeatedly calculates the same sums:

```text
❌ Calculate → discard → calculate again
```

The optimized approach stores cumulative information:

```text
✅ Calculate once → reuse
```

That is the core idea behind prefix sums.

And the deeper optimization is recognizing that even storing the prefix/suffix arrays isn't necessary when the total sum gives us enough information.

### 🧠 Pattern to Remember

When you repeatedly need sums over portions of an array, ask:

> **"Can I calculate a cumulative sum once and reuse it?"**

Prefix sums often turn repeated `O(n)` work into `O(1)` queries after an `O(n)` preprocessing pass.

```text
Brute Force
O(n²), O(1)
     │
     ▼
Prefix + Suffix
O(n), O(n)
     │
     ▼
Total Sum + Left Sum
O(n), O(1)
```

**Initial:** `O(n²)` / `O(1)` → ✅ Accepted
**Optimized:** `O(n)` / `O(n)` → ✅ Accepted
**Further optimization:** `O(n)` / `O(1)` → ⭐ Better
